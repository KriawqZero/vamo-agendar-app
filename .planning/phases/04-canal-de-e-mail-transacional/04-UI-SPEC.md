# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Two surfaces, two rendering engines.** This phase's dominant deliverable is an **HTML
transactional email** rendered by third-party mail clients (no Tailwind, no cascade, no web
fonts, table layout, inline styles). Its secondary deliverable is a **single optional field**
added to the existing dashboard perfil form (Tailwind v4, `zinc`, mobile-first). Every token
below is declared **once** and then mapped to each engine, because the same hex has to survive
two very different renderers.

| Surface | Where | Engine | Consumers downstream |
|---------|-------|--------|----------------------|
| **A — E-mail de boas-vindas** | `src/emails/BoasVindas.tsx` + `src/emails/layout/LayoutBase.tsx` | `react-email` → HTML string + plain text | Phase 5 (EML-03) and Phase 9 (EML-02) **inherit `LayoutBase`** |
| **B — Campo `email_contato`** | `src/app/dashboard/agenda/AgendaClient.tsx`, aba "Perfil da Empresa" | Tailwind v4 / React 19 | none |

⚠️ **Surface A is not a web page.** Everything in `src/app/globals.css` — custom properties,
`@theme inline`, `dark:` variants, `next/font` — is unavailable there. Values are literal hex,
literal px, inline `style={{}}`. Values below are duplicated on purpose; that duplication is
the contract, not an oversight.

## Design System

| Property | Value |
|----------|-------|
| Tool | **none** (no shadcn) — the project already carries its own token layer in `src/app/globals.css` (`--palco/--bastidor/--giz/--marca/--marca-forte`, mapped through `@theme inline`) |
| Preset | not applicable |
| Component library | **Surface A:** `react-email` `^6.9.2` (`Html`, `Head`, `Preview`, `Body`, `Container`, `Section`, `Row`, `Column`, `Img`, `Link`, `Text`, `Hr`) — per RESEARCH C-01, **not** `@react-email/components`, which is deprecated. **Surface B:** none — hand-written Tailwind, matching the sibling fields in the same form |
| Icon library | **none in this phase.** Surface A ships zero icons (image-to-text ratio is exactly what SC4 measures); Surface B adds no icon, matching the `Instagram`/`Endereço` fields beside it |
| Font | **Surface A:** `'Poppins', 'Segoe UI', Roboto, Helvetica, Arial, sans-serif`, declared **inline on every text node**, with **no `<link>` and no `@import`** — Gmail and Outlook strip webfonts, so Poppins renders only where it is already installed and everything else falls back silently. **Surface B:** unchanged — Geist for body, Poppins for display, already wired by `next/font` in `src/app/layout.tsx` |

**Why no shadcn (gate outcome).** `components.json` is absent and this was recorded as
`Tool: none` rather than initialized, on three grounds: (1) the project has a complete,
owner-approved token system already in `globals.css`, built from the paid brand manual;
(2) `CLAUDE.md` forbids unrequested abstraction layers; (3) the phase's primary artifact is an
HTML email, where shadcn/Radix cannot run at all. **This is a researcher decision, not owner
consent** — the owner can overturn it, and doing so would be a project-wide change, not a
Phase 4 change.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage — Surface A (e-mail, literal px) | Usage — Surface B (dashboard, Tailwind) |
|-------|-------|----------------------------------------|------------------------------------------|
| xs | 4px | gap between the CTA label and nothing else; border radius of the fallback-URL box | `space-y-1` inside the field group |
| sm | 8px | button border-radius; padding under the H1 | `mt-1` on the helper text |
| md | 16px | paragraph bottom margin; horizontal padding of the footer | `gap-4` in the `grid-cols-1 md:grid-cols-2` row |
| lg | 24px | card horizontal padding (mobile-safe); vertical gap between blocks | `p-6` on the perfil card (existing) |
| xl | 32px | card top/bottom padding; space above the CTA | — |
| 2xl | 48px | space between the content card and the footer | — |
| 3xl | 64px | height of the solid brand band at the top (D-17) | — |

**Exceptions (all still multiples of 4, listed because they are fixed constants, not choices):**

- **Email container width: `600px`.** Industry constant — the widest reliable width across
  Outlook desktop and mobile clients. Not negotiable, not derived from the scale.
- **Logo rendered width: `160px`** (height `52px`, preserving the 3005×973 ratio of the
  approved artwork). Asset is exported at `480×156` for 3× displays.
- **CTA minimum tap target: `44px` tall** (`padding: 12px 24px` on a 16px/1.25 label lands at
  44px). Touch-target floor; do not shrink it to fit the scale.
- Surface A uses **px only**. No `rem`, no `em`, no `%` on font sizes — Outlook resolves them
  unpredictably.

## Typography

Exactly **4 sizes**, exactly **2 weights**. Both surfaces.

| Role | Size | Weight | Line Height | Where |
|------|------|--------|-------------|-------|
| Body | 16px | 400 | 1.5 (`24px`) | E-mail paragraphs; CTA button label (at 600); dashboard input text |
| Label | 14px | 400 | 1.5 (`21px`) | E-mail footer and the copy-paste URL line; dashboard helper text and inline validation |
| Heading | 20px | 600 | 1.3 (`26px`) | Reserved for Phases 5 and 9 (section titles inside `LayoutBase`) — **unused in the boas-vindas e-mail**, which has a single title |
| Display | 28px | 600 | 1.2 (`34px`) | The one `<h1>` of the e-mail |

**Weights:** `400` (regular) and `600` (semibold). Nothing else — no 300, no 500, no 700.
When Poppins is absent the fallback stack synthesizes 600 as its own bold; that is acceptable
and expected.

**Surface A rules that override any instinct from the web codebase:**

- Line height is written in **px**, not as a unitless ratio — Outlook drops unitless values.
- Every `<td>`/`<p>` carries its own `font-family`, `font-size`, `line-height` and `color`
  inline. Nothing inherits reliably.
- Dashboard-side small text stays on the existing `text-xs` label idiom of the sibling fields
  (`text-xs font-bold uppercase text-zinc-400`) — Surface B matches its neighbours, it does not
  import the e-mail scale.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` | The content card of the e-mail — every paragraph, the fallback URL box, all reading area. Surface B: the existing `bg-white dark:bg-zinc-900` card, unchanged |
| Secondary (30%) | `#F7F8FC` | Outer canvas behind the card and the footer strip (this is `--palco`, the brand's "papel" tone, hard-coded). Surface B: the existing `bg-zinc-50 dark:bg-zinc-900` input fill, unchanged |
| Accent (10%) | `#3961D5` | See the reserved-for list below — three places, no fourth |
| Destructive | `#DC2626` (`red-600`) | **Surface B only**, inline validation text and the existing error banner border. **This phase introduces no destructive action** — the row exists so nobody invents one |

**Accent reserved for — the complete list, e-mail:**

1. **The solid band at the top of the e-mail** (`background-color: #3961D5`, height 64px) — the
   `faixa` of D-17.
2. **The inline text link** that repeats the booking URL under the button.
3. Nothing else. No tinted borders, no colored headings, no highlighted words, no colored
   footer text.

**Emphasis tone — one element only:**

| Role | Value | Usage |
|------|-------|-------|
| Emphasis | `#4219B0` (roxo do wordmark) | **The primary CTA button fill, and nothing else.** White 16px/600 label on it clears contrast comfortably, and it reads as a deliberate second brand tone rather than a second call to action |

**Text tones (not surfaces, therefore outside the 60/30/10 split):**

| Role | Value | Usage |
|------|-------|-------|
| Primary text | `#14172B` | E-mail headings and paragraphs (this is `--giz`, the manual's tinta-navy, hard-coded) |
| Secondary text | `#565C76` | E-mail footer only (this is `--névoa`, hard-coded) |
| On-accent text | `#FFFFFF` | The CTA label and the `alt` fallback over the band |

### Locked color constraints — do not "improve" these

- 🔒 **The band is solid. There is no gradient.** D-17 rejected both VML and CSS
  `background-image`, and the reason was consistency, not capability: Outlook desktop would
  show the solid fallback while Gmail showed the gradient, so the same e-mail would look like
  two different products. Adding `linear-gradient(#3DBAED, #3961D5)` "as progressive
  enhancement" reopens exactly the inconsistency the decision closed. `#3DBAED` (ciano) does
  **not** appear anywhere in this e-mail.
- 🔒 **No `dark:` anything on Surface A.** The e-mail declares
  `<meta name="color-scheme" content="light">` and `<meta name="supported-color-schemes" content="light">`,
  and sets an explicit `background-color` on **every** `<td>`. Clients that force dark mode
  (Outlook mobile, Apple Mail) recolor undeclared backgrounds and leave declared text
  untouched — which is how `#14172B` text ends up on a black card and disappears.
- 🔒 **The image budget is one image: the logo.** No hero, no illustration, no social icons,
  no badge, no divider image. Image-to-text ratio is the signal SC4 measures (RESEARCH,
  §Entregabilidade); a decorative second image spends the phase's own success criterion.
- 🔒 **The e-mail carries exactly one hyperlink target: the tenant's `/book/[slug]`.** It
  appears twice (button + text URL), pointing at the same absolute URL on
  `vamoagendar.com.br`. No dashboard link, no site link, no Instagram, no help link. Link
  count and footer complexity weigh with the image ratio in tab classification, and every link
  must stay on the sending domain.

### Asset contract — the logo

| Property | Value |
|----------|-------|
| Source artwork | `artes-aprovadas-design/Fundo_escuro/logo_fundo_escuro.png` (3005×973 RGBA) — the **light-on-dark** variant, because it sits on the `#3961D5` band |
| Exported to | `public/email-logo.png`, **480×156**, RGB (no alpha), **flattened onto `#3961D5`** |
| Referenced as | `` `${process.env.APP_URL}/email-logo.png` `` — absolute, same domain as the sender. Never a relative path, never the Supabase Storage bucket (that bucket is tenant-scoped, and an off-domain asset is a deliverability negative) |
| Rendered at | `width="160" height="52"`, both as HTML attributes **and** inline style |
| `alt` | `VamoAgendar` — must be legible white-on-blue when images are blocked, so `color: #FFFFFF` is set on the `<img>` itself |
| Never | SVG (Gmail drops it), data URI, `cid:` attachment |

**Why flattened, not transparent:** RGBA over a colored table cell is where Outlook desktop
invents a white rectangle. Baking `#3961D5` into the PNG costs nothing and removes the failure
mode entirely.

## Copywriting Contract

All user-facing strings are **pt-BR with full diacritics**. Tone follows
`docs/05-PRODUTO_E_VISAO.md` and the global public-text rule: nothing that reads as a template,
no invented numbers, no testimonials (there is no customer yet), no exclamation marks, no
emoji, no "parabéns pela sua jornada".

`{estabelecimento}` = `perfis_empresas.nome_empresa`. `{slug}` = `perfis_empresas.slug`.

### Surface A — e-mail de boas-vindas

| Element | Copy |
|---------|------|
| **Remetente** (already built, `montarRemetente`) | `"{estabelecimento} via VamoAgendar" <naoresponda@mail.vamoagendar.com.br>` |
| **Assunto** | `Seu link de agendamento está pronto` |
| **Preheader** (hidden preview text, `<Preview>`) | `Compartilhe esse endereço e seus clientes marcam horário sem criar conta.` |
| **Título (H1)** | `Seu link de agendamento está pronto` |
| **Parágrafo 1** | `A conta do {estabelecimento} está criada. Este é o endereço que seus clientes usam para marcar horário:` |
| **Primary CTA** (the one button) | `Abrir minha página de agendamento` |
| **URL abaixo do botão** (copy-paste fallback) | `vamoagendar.com.br/book/{slug}` |
| **Parágrafo 2** | `Coloque o link na bio do Instagram, no status do WhatsApp ou mande direto para quem pedir horário. Quem abrir escolhe o serviço, o dia e a hora sem baixar aplicativo e sem criar conta.` |
| **Parágrafo 3** | `Os serviços e os horários que você cadastrar no painel aparecem nessa página automaticamente.` |
| **Rodapé, linha 1** | `Você recebeu este e-mail porque criou uma conta no VamoAgendar.` |
| **Rodapé, linha 2** | `Esta é uma mensagem automática. Este endereço não recebe respostas.` |
| **Rodapé, linha 3** | `VamoAgendar` |

**Copy rules that carry a decision:**

- 🔒 **Rodapé linha 2 is mandatory and cannot be softened.** D-02 locked "no reply-to", and
  `naoresponda@` is literal — the domain has no MX record, so a reply is swallowed with no
  bounce and no human ever sees it. Telling the reader is the only honest option. Any future
  agent that "fixes" this by adding a reply-to is contradicting D-02/D-03/D-04 in writing.
- **No unsubscribe link.** This is transactional mail, not marketing; an opt-out here would
  mean opting out of the account's own operational messages. Also no preference centre, no
  "gerenciar e-mails".
- **Parágrafo 3 deliberately names the painel without linking to it** — the one-link budget
  above.
- The subject line avoids `!`, `grátis`, `promoção`, `oferta`, `agora`, ALL-CAPS and emoji.
  Not superstition: it is a domain with zero reputation history, and SC4 is measured in
  Gmail's own tabs.

### Surface A — plain-text alternative (D-03a)

The text version is **derived**, never hand-written: `render(node, { plainText: true })` on
the same tree. Which means the HTML has to be authored so the derived text reads as a letter:

| Requirement | Consequence for the component |
|-------------|-------------------------------|
| The URL must survive | The absolute URL appears as **literal text** in a `<Text>`, not only as the button's `href`. A button whose label is "Abrir minha página de agendamento" flattens to that phrase and loses the address |
| No decoration in the text output | No ASCII rules, no `———`, no emoji, no `*` bullets. `<Hr>` flattens to a blank line, which is fine |
| Footer order is preserved | The three footer lines flatten in order and remain readable as three short sentences |
| Never | `render(node, { pretty: true })` in production — it pulls prettier into the request path for nothing |

### Surface B — campo `email_contato` (dashboard, aba "Perfil da Empresa")

| Element | Copy |
|---------|------|
| **Label** | `E-mail de contato` |
| **Placeholder** | `voce@exemplo.com.br` |
| **Helper text** (below the input, `text-xs text-zinc-500 mt-1`) | `Se ficar em branco, usamos o e-mail da sua conta de acesso. Só o VamoAgendar escreve para este endereço — ele não aparece na sua página de agendamento.` |
| **Primary CTA** | `Salvar Perfil` — the form's **existing** submit button. This phase adds **no new button** |
| **Pending state** | `Salvando...` — existing `isPending` behaviour, unchanged |
| **Success banner** | `Perfil salvo com sucesso.` — existing `msgPerfil` mechanism, unchanged |
| **Empty state** | Blank input is a **valid, expected state**, not an error: the helper text above is the empty state. No placeholder-as-label, no warning styling, no nudge to fill it |
| **Error state — invalid format** | `Digite um e-mail válido, como voce@exemplo.com.br.` — inline, below the input, `text-xs text-red-600 dark:text-red-400` |
| **Error state — save failed** | `Não foi possível salvar o perfil agora. Tente de novo em alguns instantes.` — through the existing error banner (`bg-red-50 … border-red-200`), never a raw Supabase/Clerk string |
| **Destructive confirmation** | **None.** Clearing the field is not destructive — it restores the Clerk address as the destination. No modal, no "tem certeza", no red button |

**Field placement:** inside the existing `grid grid-cols-1 md:grid-cols-2 gap-4` row, paired
with `WhatsApp de Contato público` — the two "how we reach you" fields sit together. Mobile
stacks them, which is the mobile-first default already in that form. `type="email"`,
`maxLength={254}`, `autoComplete="email"`, `inputMode="email"`.

🔒 **`email_contato` is never rendered on `/book/[slug]`.** It is not part of the
`personalizacao` payload of `obterDadosBookingPublico`, and the column does not get `anon`
access (RESEARCH §Perguntas em aberto #1). The helper text states this to the professional,
and the contract states it here so no future UI "completes the profile card" with it.

> state coverage and REFERENCES those rows rather than restating the copy (de-dup).

Applicable state considerations resolved: **9 covered, 4 backstop, 1 unresolved**

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | `email_contato` input | ✅ covered | Blank is a valid state; the Surface B "Empty state" row renders as helper text, with no warning styling and no error |
| empty | welcome e-mail, no usable address | ✅ covered | D-10: nothing is rendered and nothing is sent — the row is written as `sem_destinatario` and the dashboard opens normally. There is no user-facing empty UI, by design |
| loading | perfil form submit | ✅ covered | Existing `isPending` swaps the button label to `Salvando...` and disables it — unchanged behaviour, the new field just joins the same form |
| loading | welcome e-mail dispatch | ✅ covered | D-09: the send runs inside `after()`, after the response is flushed. The dashboard shows **no** spinner, **no** toast and **no** "enviando e-mail" state — the first paint must not wait on Resend |
| error | invalid e-mail format | ✅ covered | Inline message under the input; see Surface B "Error state — invalid format". Validation runs on the server action too, never only in the island |
| error | save failure | ✅ covered | Existing red banner with the friendly pt-BR string; raw provider errors never reach the UI |
| error | send failure (`falhou`/`rejeitado`) | ✅ covered | Invisible to the professional by design (Regra de Falha Silenciosa) — it goes to the audit table and Sentry. Telling the professional in-dashboard is the deferred Phase 11 idea; do **not** build a banner for it here |
| populated | `email_contato` with a value | ✅ covered | Standard input rendering, same classes as the sibling `Endereço` field |
| zero-one-many | welcome e-mail per tenant | ✅ covered | Exactly one, forever — enforced by the partial unique index of D-06/D-07, not by UI state. There is no "resend" button and no "already sent" indicator in this phase |
| long-text | very long `{estabelecimento}` in the H1 and the `from` display name | 🧪 backstop | Header side is already sanitized by `montarRemetente`; the H1 must **wrap**, never truncate, never `white-space: nowrap`. Verify with a ~60-character establishment name in the local preview (`email dev`) at 320px |
| long-text | long `{slug}` in the copy-paste URL line | 🧪 backstop | The URL `<Text>` carries `word-break: break-all` so it wraps inside the 600px container instead of forcing horizontal scroll in mobile clients. Verify in the preview at 320px |
| images-off | logo blocked (common in corporate Outlook) | 🧪 backstop | The band is a CSS background colour, so the top still renders as a blue bar; `alt="VamoAgendar"` in white must be readable on it. Verified in the SC4 UAT, corporate-domain leg |
| forced-dark-mode | e-mail card and text | 🧪 backstop | `color-scheme: light` + explicit `background-color` on every `<td>`; verify in Apple Mail and Outlook mobile with dark mode on, that `#14172B` text is not left on a recoloured surface. Part of the SC4 UAT sweep |
| tab-classification | the whole message | ⚠ unresolved | Which Gmail tab the e-mail lands in cannot be predicted or asserted — it is holistic and depends on reputation and engagement, which a zero-history domain does not have. Deliberately left as an assumption: SC4 is **measurement by the owner**, not a claim any executor can make |

## Registry Safety

No shadcn registry is in play (`Tool: none`), so the shadcn vetting gate does not apply. The
equivalent third-party surface for this phase is the **npm package supplying the e-mail
components**, and it was audited during research.

| Registry | Blocks Used | Safety Gate |
|----------|-------------|-------------|
| shadcn official | none | not applicable — shadcn is not initialized in this project |
| third-party shadcn registries | none declared | not applicable |
| npm — `react-email@^6.9.2` (`dependencies`) | `Html`, `Head`, `Preview`, `Body`, `Container`, `Section`, `Row`, `Column`, `Img`, `Link`, `Text`, `Hr`, `render` | `gsd-tools query package-legitimacy check` run **2026-08-07**: verdict **SUS (`too-new`)** — the signal is last-publish date (2026-08-07), not package age. | npm — `@react-email/ui@^6.9.2` (`devDependencies`, local preview app only) | `email dev` preview server | Same audit, same date, verdict **SUS (`too-new`)**; 692.732 downloads/week, `"postinstall": null`. Covered by the same `checkpoint:human-verify` |

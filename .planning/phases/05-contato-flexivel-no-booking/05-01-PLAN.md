# Plan 05-01 — Migration de Schema `clientes` e RPC de Deduplicação Atômica

## Objective

Tornar a coluna `telefone` na tabela `clientes` opcional (`NULLABLE`), adicionar a constraint `CHECK (telefone IS NOT NULL OR email IS NOT NULL)` e criar índices parciais por tenant. Atualizar a RPC atômica `reaproveitar_ou_criar_cliente` para realizar o lookup deduplicado (WhatsApp primeiro, E-mail em seguida), atualizando dados cadastrais ausentes em clientes já existentes e evitando duplicatas no banco de dados.

## Context & Architecture

Atualmente a tabela `clientes` exige `telefone TEXT NOT NULL`. Para permitir agendamentos com apenas e-mail (BOO-01), precisamos permitir `telefone` como `NULL`, mantendo a garantia de integridade de que ao menos um meio de contato existe.

Além disso, a deduplicação de clientes (BOO-03) exige busca prioritária por telefone. Se não encontrado (ou se telefone não foi fornecido), busca por e-mail (normalizado em minúsculas). Se o cliente existir em banco, o registro é reaproveitado e qualquer dado de contato ausente (ex: novo e-mail informado por cliente achado via telefone) é atualizado atômica e silenciosamente.

## Proposed Changes

### 1. Database Migration
#### [NEW] [20260808100000_contato_flexivel_clientes.sql](file:///home/marcilio/Files/VamoAgendar/vamo-agendar-app/supabase/migrations/20260808100000_contato_flexivel_clientes.sql)

- Executar alteração de DDL na tabela `clientes`:
  ```sql
  ALTER TABLE clientes ALTER COLUMN telefone DROP NOT NULL;
  ALTER TABLE clientes ADD CONSTRAINT ck_clientes_telefone_ou_email CHECK (telefone IS NOT NULL OR email IS NOT NULL);
  CREATE INDEX IF NOT EXISTS idx_clientes_tenant_telefone ON clientes (tenant_id, telefone) WHERE telefone IS NOT NULL;
  CREATE INDEX IF NOT EXISTS idx_clientes_tenant_email ON clientes (tenant_id, lower(email)) WHERE email IS NOT NULL;
  ```
- Atualizar a função RPC `reaproveitar_ou_criar_cliente`:
  - Parâmetros: `p_tenant_id TEXT`, `p_telefone TEXT DEFAULT NULL`, `p_nome TEXT DEFAULT NULL`, `p_email TEXT DEFAULT NULL`.
  - Lógica interna:
    1. Se `p_telefone` for não-nulo, buscar `id, email, nome` em `clientes` onde `tenant_id = p_tenant_id AND telefone = p_telefone`.
       - Se encontrado: se `p_email` for não-nulo e `email` for nulo no registro, atualizar `email = p_email`. Se `p_nome` for fornecido e diferente, opcionalmente atualizar. Retornar `id`.
    2. Se não encontrado e `p_email` for não-nulo, buscar `id, telefone, nome` em `clientes` onde `tenant_id = p_tenant_id AND lower(email) = lower(p_email)`.
       - Se encontrado: se `p_telefone` for não-nulo e `telefone` for nulo no registro, atualizar `telefone = p_telefone`. Retornar `id`.
    3. Se não encontrado em nenhuma das buscas:
       - Inserir novo registro: `INSERT INTO clientes (tenant_id, telefone, nome, email) VALUES (p_tenant_id, p_telefone, p_nome, p_email) RETURNING id`.
